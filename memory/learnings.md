## Patterns

### 2026-07-04 — Enum query-param filters need explicit validation, or Prisma throws an unhandled 500
`GuidelinesService#list` cast an untrusted `?type=` query string straight into a Prisma `where` filter (`type as never`) without checking it against the `GuidelineType` enum first. A garbage value (e.g. `?type=NOT_A_REAL_TYPE`) isn't rejected by class-validator (it's a plain `@Query()` string, not a DTO field) — it reaches Prisma, which throws an unhandled runtime validation error, surfacing as a raw 500 instead of a clean 400. Caught live during Stage 5 verify (reproduced against a running server), not by the automated test suite (which only tested valid enum values). Fix: validate any enum-typed query/filter param explicitly (`Object.values(EnumType).includes(value)`) and throw `BadRequestException` before it reaches the ORM — DTOs with `@IsEnum` only protect body fields, not query params read via `@Query()`. Apply this check to any future `?type=`/`?status=`-style filter (e.g. Tasks already validates `status` via the DTO on PATCH, but its own `GET /tasks` has no filter yet — check if one is added later).
**Files**: `apps/api/src/guidelines/guidelines.service.ts`, `apps/api/src/guidelines/guidelines.e2e.spec.ts`

### 2026-07-03 — Kitchen-scoped controller pattern: derive caller's kitchenId server-side, never trust `:id`
Any route taking a `:id` URL param for a tenant-scoped resource must resolve the caller's own scope (kitchenId/orgId) from their authenticated user record first, then compare/query against that — never query directly by the untrusted `:id` and treat a 403 as sufficient (it leaks existence). Mismatch → 404. See `KitchensController.callerKitchenId()` (T002) as the reference implementation; reused for T004's `InventoryController`.
**Files**: `apps/api/src/kitchens/kitchens.controller.ts`, `apps/api/src/kitchens/kitchens.service.ts`, `apps/api/src/inventory/inventory.controller.ts`

### 2026-07-04 — Field-name allowlist for restricted-role PATCH doesn't scope field *content*
T008's `TasksService#update` originally let any non-writer touch `status`/`checklistItems` via an `Object.keys(dto)` allowlist check — but once `checklistItems` is allowed, the caller can replace the *entire* array (rewrite item text, delete items, add new ones), not just flip `done` on existing ones. A field-name allowlist is not the same guarantee as "may only toggle done" — if the intent is narrower than "may write this whole field," diff incoming vs. existing content per-item, don't just allowlist the field name. Left as a P2 in T008's code-review (not blocking), flagged here so future self-service-update tasks (e.g. Comments/T015 edit) don't repeat the gap.
**Update (2026-07-05, T019)**: this allowlist path is now STAFF-only — `Role.VIEWER` is rejected earlier in the same method (see `memory/decisions.md`'s T019 correction entry), since Viewer never gets past the ownership check to reach the field-content question at all.
**Files**: `apps/api/src/tasks/tasks.service.ts`

### 2026-07-05 — RBAC audits need matrix-style tests, not per-task tests, to catch role-omission gaps
T004–T011 each tested their own module's RBAC correctly in isolation, but none of them explicitly exercised the Viewer role against write endpoints (T008/T011's own-task tests only checked "Staff can complete their own Task" and "Staff cannot complete someone else's" — never "can Viewer complete their own Task"). The gap survived four merged tasks and two Stage 4 security-reviews before T019's dedicated (module × role × verb) matrix test caught it. Per-task, per-feature test suites are necessary but not sufficient for RBAC completeness — a dedicated cross-cutting matrix audit (one test file enumerating every module × every role × every verb) is needed to catch omission gaps that any single task's test suite, written by whoever built that one feature, is structurally unlikely to think to check.
**Files**: `apps/api/src/rbac-audit/rbac-matrix.e2e.spec.ts`, `apps/api/src/tasks/tasks.service.ts`, `apps/api/src/tasks/complete/task-completion.service.ts`

### 2026-07-03 — Append-only audit-ledger pattern: no PATCH/DELETE route, no cached running balance
For entities requiring an immutable audit trail (T004's `StockMovement`; likely relevant to future audit-log-style entities e.g. ShiftLog/T014, Comments/T015 edit history), don't expose an update/delete endpoint at all — the absence of the route, not application-level rejection, is what makes it append-only, and it's what an e2e test should assert (expect a 404 for the unmapped route, not a 403). Avoid a cached derived-state column (e.g. running stock balance) alongside the ledger — deriving it by summing/querying avoids read-modify-write races on concurrent writes entirely, at the cost of a more expensive read (acceptable at this MVP's scale).
**Files**: `apps/api/src/inventory/inventory.controller.ts`, `apps/api/src/inventory/inventory.service.ts`

## Gotchas

### 2026-07-03 — TASK_GUIDE's stated "Verification Command" can be stale/wrong — always run it, don't just trust it
T003's TASK_GUIDE specified `npm --prefix apps/web run test -- layout routing`, but no test file matched that Vitest filter (actual files: `App.test.tsx`, `AuthGuard.test.tsx`, `LoginPage.test.tsx`) — the command failed with "No test files found" despite the underlying suite being fully green. Caught only by actually running the command at Stage 4/5 review rather than trusting the implementer's report. Corrected in the guide to the full-suite command.
**Update 2026-07-05 (T016)**: same trap, different shape — the guide's `npm --prefix apps/web run test -- notifications` (lowercase, plural) didn't match `NotificationBell.test.tsx` because Vitest's filename-substring filter is case-sensitive and the component folder is `NotificationBell` (capital N, no trailing "s"). Working filter: `-- Notification`. Pattern: whenever a TASK_GUIDE's verification command uses `-- <keyword>`, that keyword must be a literal substring of the actual test filename, not the feature/entity name in prose — always run it once yourself before trusting a "tests pass" report; a guessed filter can silently no-op while an unrelated suite reports green.
**Files**: `tasks/TASK_GUIDE_T003.md`, `tasks/TASK_GUIDE_T016.md`

### 2026-07-03 — Evidence Gate hook (`pre_bash_block_unsafe_merge.py`) checks the *root* `tasks/` dir, not worktree copies, and requires "pass" in the THIRD cell
The PreToolUse hook blocking `git push`/`merge`/`rebase` reads `tasks/TASK_GUIDE_T00X.md` from the main repo's working tree, not from `.claude/worktrees/T00X/tasks/`. Evidence filled only in the worktree copy won't satisfy the gate — copy the finished TASK_GUIDE into the main repo's `tasks/` dir before merging. Its regex is `verify\s*\|[^|\n]+\|[^|\n]*pass` — three requirements, all must hold: (1) the literal word `verify` immediately followed by a pipe as the Evidence table's first cell (a bare `| verify |` label — the template's own `` `verify` skill — works in running app `` phrasing does NOT match, backtick breaks `\s*`); (2) any content in the second (Result) cell; (3) the literal substring "pass" (case-insensitive) somewhere in the THIRD (Notes) cell specifically — a "☒ pass" in the Result cell alone does NOT satisfy this, since the regex's final `[^|\n]*pass` only scans past the *second* pipe. Confirmed via T002's working row (`...all held. See PASS verification report...`) vs T004's initial attempt which needed an explicit "— PASS." appended to the Notes cell. Rediscovering this from scratch cost ~4 failed merge attempts; test the exact regex with `python3 -c "import re; print(bool(re.search(...)))"` against the guide file before retrying a blocked merge. **Update 2026-07-04**: after T008 hit this same trap again (plus initially reported "Done" to the user without the Evidence table filled at all — caught by user review, not process), pre-emptively relabeled the `verify` row to the bare form and added an explicit "Evidence is a required document" reminder in all not-yet-started guides (T006/T007/T009-T023) and in the master `templates/TASK_GUIDE_template.md`, so future tasks don't rediscover either issue.
**Files**: `.claude/hooks/pre_bash_block_unsafe_merge.py`, `tasks/TASK_GUIDE_T002.md`, `tasks/TASK_GUIDE_T003.md`, `tasks/TASK_GUIDE_T004.md`, `tasks/TASK_GUIDE_T006.md`–`TASK_GUIDE_T023.md`, `templates/TASK_GUIDE_template.md`
**Update 2026-07-05 (T007)**: hit again — the template reminder tells you the rule but doesn't force compliance; a naturally-written Notes cell ("...both green post-change.") still lacked the literal token. Fix going forward: always start the Notes cell with a standalone `PASS —` prefix (not just anywhere in the prose) so it's impossible to omit by accident. Don't trust the reminder text alone; grep-test the row before attempting the merge.
**Update 2026-07-05 (T012), same day, different failure mode**: fixing the T007 gotcha introduced a NEW variant — the sub-agent wrote `| PASS — verify | pass | <notes with no literal "pass"> |`, putting the `PASS —` prefix on the FIRST cell (the row label) instead of the THIRD cell (Notes). The regex only checks cell 3, so this still failed to match. The cell layout is `| verify | <result> | <notes> |` — three cells, and "pass" must land specifically in cell 3. Do not paraphrase this as "put PASS somewhere in the row" — the exact instruction is "the Notes/third cell must literally contain the substring pass", full stop. Always `python3 -c "import re; print(re.search(r'verify\s*\|[^|\n]+\|[^|\n]*pass', open(path).read(), re.I))"` against the guide file before attempting the merge, don't just eyeball it.

### 2026-07-03 — Agent tool's `isolation: "worktree"` conflicts with a Supervisor-pre-created worktree
When the Supervisor already runs `git worktree add .claude/worktrees/T00X -b task/T00X-... develop` before spawning the implementer, passing `isolation: "worktree"` on the `Agent` tool call gives the spawned agent a *different*, separate sandbox worktree (e.g. `.claude/worktrees/agent-<id>`) with none of the monorepo checked out — the agent can Read/Bash-explore the intended T00X path (visible, not writable) but Edit/Write are sandboxed to the empty agent worktree and refuse to touch the T00X path. First occurrence on T005: the agent correctly stopped and asked instead of guessing (per the general-agent-template rule), no code was written, and the empty sandbox worktree auto-cleaned itself on since it had no changes. Fix: when a worktree was already created manually for the task, omit `isolation` entirely on the `Agent` call and point the prompt directly at the existing worktree path — do not pass `isolation: "worktree"` in that case.
**Files**: (process-only, no repo files)

### 2026-07-04 — easy-ui-mcp toolset has no viewport-resize primitive
The MCP tool list (`ui_start_session`, `ui_navigate`, `ui_click`, `ui_fill`, `ui_take_screenshot`, `ui_get_page_state`, `ui_assert`, `ui_end_session`) has no select-option and no viewport/resize primitive — can't drive a native `<select>` element's option choice, and can't screenshot at a specific mobile/tablet/desktop breakpoint. Workarounds used on T008: (1) for a `<select>` filter, navigate directly to the URL with the query param already set (exercises the same client-side read path as choosing the option, since state is URL-driven) instead of trying to interact with the dropdown; (2) for responsive-breakpoint UI Evidence rows, use `ui_assert` with a JS condition against the live DOM (e.g. checking a CSS class is present, checking computed `getBoundingClientRect().height >= 44` on touch targets) as a substitute for an actual resized screenshot capture.

### 2026-07-06 — merge-gate hook's regex breaks if the Evidence table's Notes cell contains a literal `|` character
`tasks/TASK_GUIDE_T023.md`'s `verify` row Notes cell quoted a `grep -E` pattern containing regex-alternation `|` characters (e.g. `"rnd_[a-z0-9]{10,}|render_api_key\s*="`). Markdown doesn't care, but `pre_bash_block_unsafe_merge.py`'s naive `verify\s*\|[^|\n]+\|[^|\n]*pass` regex treats every `|` as a column boundary — the extra pipes shifted what the hook considered the "third cell," so it never found the literal word "pass" even though the row visually and semantically had it. The hook then blocked *every* `git merge`/`push` project-wide (not just for that task) until the row was rewritten to avoid raw pipes. When writing Evidence table Notes that quote shell/regex snippets with `|`, either escape as `\|`, rephrase in prose, or move the snippet to a code block outside the table row.

### 2026-07-06 — CORRECTED: `post_agent_move_to_review.py` hook auto-moves tasks to "Ready for Review" the instant `Agent(...)` is called, not when the agent finishes
Originally misdiagnosed as sub-agents violating "don't touch PROJECT_KANBAN.md" instructions. The real cause is `.claude/hooks/post_agent_move_to_review.py`, a `PostToolUse` hook that fires after every `Agent` tool call, regex-extracts `T\d{3}` task IDs from the spawn *prompt*, and immediately moves matching lines from "In Progress" to "Ready for Review" in `PROJECT_KANBAN.md` — before the agent has done any work at all. ### 2026-07-06 — Vite preview server blocks unrecognized Host headers by default (breaks Render deploy)

### 2026-07-06 — REST CORS was hardcoded to localhost, independent of the WEB_ORIGIN env var used elsewhere
`apps/api/src/main.ts`'s `app.enableCors({ origin: 'http://localhost:8766' })` was a hardcoded literal, never wired to the `WEB_ORIGIN` env var that `RealtimeGateway`'s Socket.IO CORS config already reads — so setting `WEB_ORIGIN` on the deployed Render service (per RUNBOOK.md) fixed realtime CORS but NOT REST CORS, and every REST call (signup/login/etc.) from the deployed frontend failed the CORS preflight. ### 2026-07-06 — Full first-deploy debugging chain on Render (chronological)
The first real Render deploy of this project surfaced a chain of distinct issues, each masking the next until fixed one at a time: (1) devDependencies skipped during build (`NODE_ENV=production`) — fixed via `npm install --include=dev` in both `build` scripts; (2) `apps/api`'s compiled entry point was `dist/src/main.js` not `dist/main.js` — `start`/`start:prod` were wrong since first written; (3) Render dashboard Root Directory typo'd as `api` instead of `apps/api`; (4) `vite preview`'s default Host-header allow-list rejected Render's `*.onrender.com` domain; (5) `DATABASE_URL` set as a GitHub Actions secret, not a Render service environment variable — the two systems don't share config, a GH secret is invisible to the actual Render runtime; (6) `VITE_API_BASE_URL` set on Render but the frontend needed a fresh **build** (Vite bakes env vars in at build time, not runtime) to pick it up; (7) REST CORS hardcoded to localhost, separate from the `WEB_ORIGIN` var used only by the realtime gateway. **General lesson**: a monorepo's first production deploy to a new platform reliably surfaces N independent latent bugs that unit/e2e tests never catch, because local dev never exercises "fresh install with NODE_ENV=production," "separate build/runtime env boundaries," or "cross-origin browser request" — budget for an iterative debug loop, not a one-shot deploy.
**Files**: `apps/api/package.json`, `apps/web/package.json`, `apps/web/vite.config.ts`, `apps/api/src/main.ts`, `RUNBOOK.md`

### 2026-07-14 — Tailwind v4's bare `.border`/`.border-t`/etc. utilities default to `border-color: currentColor`, NOT the theme's `--color-border` token
Set `--knos-border: transparent` in both `[data-theme]` blocks expecting it to remove all border lines app-wide (since `@theme inline` maps `--color-border` to it, and every component uses bare `border`/`border-b`/`border-r` classes). It had **zero visible effect** — caught via live Playwright verification (`getComputedStyle(el).borderColor` read the text-color value, not transparent) before committing, not after. Root cause: Tailwind v4 changed the preflight default so bare border utilities resolve `border-color` from `currentColor`, not a theme border-color token — that only happens for explicit `border-{token}` variants (`border-t-warning`, `border-danger`, etc.), which generate their own `border-*-color` declaration referencing the named token directly. **General lesson**: don't assume a `@theme inline` custom-property mapping automatically reaches every Tailwind utility that superficially looks related (`border` "should" use `--color-border` by name-association, but doesn't in v4) — verify the actual computed style, not just visual inspection, when a token change appears to do nothing.
**Files**: `apps/web/src/index.css`

## Architecture

### 2026-07-02 — Monorepo, NestJS backend, Socket.IO realtime, cron-based recurrence
**Decision**: KitchenOS MVP is a monorepo (`/apps/web` React+TS, `/apps/api` NestJS, `/packages/shared` shared DTO/types) with PostgreSQL, custom JWT auth (org/role model), Socket.IO for realtime Task/Comment/Announcement updates, and a nightly cron job materializing recurring Task rows (not virtual/on-the-fly recurrence instances).
**Why**: Domain is RBAC-heavy (~10 entities, 4 roles) — NestJS guards/DI give one consistent enforcement point instead of hand-rolled per-route checks. Monorepo keeps API types in sync for a solo dev. Socket.IO ships correct realtime UX from day one (named MVP requirement, PRD §3.3/NFR-002) instead of a later polling-to-WS migration. Cron-generated Task rows keep per-occurrence completion and stock-deduction-on-completion (FR-008) simple to model. Full comparison in `BRAINSTORMING_LOG.md` (Option B selected over Minimalist/Express+polling and Maximalist/microservices paths).
**Files**: `/apps/api/**`, `/apps/web/**`, `/packages/shared/**`

### 2026-07-03 — RolesGuard: DB-current role, never JWT claim; 404-not-403 on cross-tenant access
**Decision**: `RolesGuard` (the single RBAC enforcement point, T002) re-reads the caller's role from Postgres on every guarded request rather than trusting a JWT claim (the JWT payload deliberately carries no `role` field). Cross-tenant resource access (e.g. `GET/PATCH /kitchens/:id` for a kitchen the caller doesn't belong to) returns 404, never 403, to avoid leaking the existence of other orgs' data.
**Why**: A role change or removal must take effect on the very next guarded call, not just after re-login (stale-JWT privilege risk). A P0 finding in Stage 4 review caught the initial version trusting `:id` from the URL without scoping to the caller's own kitchen — fixed by deriving `kitchenId` from the caller's own user record, matching `UsersService.invite`'s existing pattern.
**Files**: `apps/api/src/auth/guards/roles.guard.ts`, `apps/api/src/kitchens/kitchens.controller.ts`, `apps/api/src/kitchens/kitchens.service.ts`

### 2026-07-03 — Invite tokens expire after 7 days
**Decision**: `Invite.expiresAt` (nullable, additive migration) is set 7 days out on create/refresh; `acceptInvite` treats an expired PENDING invite the same as not-found (404), never distinguishing "expired" from "invalid" in the response.

### 2026-07-03 — StockMovement is a pure append-only ledger, no cached running balance
**Decision**: `StockMovement` rows are insert-only (no PATCH/DELETE route exists at all); `Ingredient`/`StockBatch` carry no cached quantity column that CONSUME/WASTE/ADJUST movements decrement. Current stock level, if ever needed, is derived by summing movements, not maintained as mutable state.
**Why**: Avoids any read-modify-write race on concurrent stock writes — inserts naturally can't lose an update, whereas a cached balance would need locking or optimistic-concurrency handling. Deduction-on-task-completion (T011) and low-stock alerting (T007) are explicitly out of scope for T004 and will consume this ledger, not extend it with a balance column.
**Update (2026-07-05, T011)**: The derived-balance read is now implemented — `InventoryService#currentStock(ingredientId)` sums all movements (RECEIVE/ADJUST add, CONSUME/WASTE subtract) on every call, still no cached column. Used only for the negative-stock warning in task-completion preview; never gates the deduction itself. See [[T011 stock deduction]] below.
**Files**: `apps/api/src/inventory/inventory.service.ts`, `apps/api/src/inventory/inventory.controller.ts`, `apps/api/prisma/schema.prisma`

### 2026-07-03 — Recipe cost_computed is always live-derived, never stored; versioning via a separate append-only RecipeVersion table
**Decision**: `Recipe`/`RecipeIngredient` store no cost field at all — `cost_computed` is recalculated on every read and write from the CURRENT `Ingredient.cost_per_unit` (T004's module). Version history uses a dedicated `RecipeVersion` table (full snapshot per edit: name/steps/servings/ingredients + the cost as computed at that save time) rather than inline JSON on `Recipe`, with no PATCH/DELETE route — matching T004's `StockMovement` append-only pattern. `Recipe.version` is a plain incrementing int bumped on every create/update, written inside the same `$transaction` as the Recipe/RecipeIngredient rows so a partial failure can't leave version history out of sync.
**Why**: The live-cost behavior is an explicit MVP directive in `TASK_GUIDE_T005.md`/`PROJECT_SPEC.md` (a Recipe's displayed cost should reflect today's ingredient prices, not a stale snapshot from creation time) — confirmed by Stage 5 verify: changing an Ingredient's price after Recipe creation immediately changes the Recipe's `costComputed` on next read, no recipe edit needed. The separate `RecipeVersion` table (vs. inline JSON) was chosen by the implementer to reuse the repo's established append-only-ledger shape and let prior versions be queried directly without ever mutating history rows.
**Files**: `apps/api/src/recipes/recipes.service.ts`, `apps/api/src/recipes/recipes.controller.ts`, `apps/api/prisma/schema.prisma`

### 2026-07-03 — RecipeIngredient → Ingredient FK is onDelete: Restrict
**Decision**: `recipe_ingredients.ingredient_id` references `ingredients.id` with `ON DELETE RESTRICT` — deleting an Ingredient referenced by any RecipeIngredient is blocked at the DB level.
**Why**: T004's Inventory module has no Ingredient-delete endpoint at all yet, so this constraint is currently inert in practice, but it's the simpler, safer default that prevents silent orphaning (a Recipe pointing at a nonexistent Ingredient) if a delete endpoint is ever added — chosen over the alternative of showing "ingredient no longer available" in the API response, which the TASK_GUIDE's edge-case checklist left as an open choice.
**Files**: `apps/api/prisma/schema.prisma`, `apps/api/prisma/migrations/20260703104034_add_recipes/migration.sql`

### 2026-07-05 — T011 stock deduction: RBAC bypass is intentional, negative stock allowed+flagged, atomic claim guards double-completion
**Decision**: `TaskCompletionController` (`POST /tasks/:id/complete/{preview,confirm}`) is deliberately NOT decorated with `@Roles(...WRITE_ROLES)`. Authorization instead lives inside `TaskCompletionService#loadTask`: a WRITE_ROLES caller (OWNER/ADMIN/CHEF) may complete any Task in their Kitchen; a non-writer STAFF caller may only complete a Task assigned to themselves (VIEWER is always denied — see the 2026-07-05 T019 correction below). The resulting `StockMovement(CONSUME)` write therefore happens for a STAFF user with no direct inventory-write permission — this is intentional, since the deduction is a side effect of a task-completion action they ARE permitted to perform, not a direct inventory edit. Deduction quantity is `RecipeIngredient.qty (per serving) × Recipe.servings`; if it would push `currentStock` negative, the write still proceeds (`wouldGoNegative`/`hasNegativeWarning` flags returned to the client) — never blocked. Same-task double-completion is guarded by an atomic conditional `tx.task.updateMany({ where: { id, status: { not: 'DONE' } }, data: { status: 'DONE' } })` inside the confirm transaction — 0 rows affected means another request already claimed it, and a 409 is thrown; this works under default read-committed isolation without needing serializable transactions. Cross-task concurrent deductions on the same Ingredient need no special locking at all since StockMovement is append-only (see the 2026-07-03 entry above).
**Why**: Matches FR-008 (confirm-before-deduct, not silent) as locked in Stage 0.5a grilling. The atomic-`updateMany`-as-claim pattern was chosen over a separate read-then-write check specifically to close the double-completion race without paying for a serializable transaction.
**Correction (2026-07-05, T019)**: this entry originally said "STAFF/VIEWER can complete only their own Tasks" — that was wrong and shipped a real gap. FR-018 states Viewer is strictly read-only; a Viewer must never be able to complete a Task (or trigger its stock deduction) even if assigned to it. Fixed in `TaskCompletionService#loadTask` (and the analogous `TasksService#update` for PATCH status/checklist) to explicitly throw `ForbiddenException` for `Role.VIEWER` before the Staff-ownership check. Caught by T019's RBAC matrix audit, not by T008/T011's own tests (Viewer was never exercised there).
**Files**: `apps/api/src/tasks/complete/task-completion.controller.ts`, `apps/api/src/tasks/complete/task-completion.service.ts`, `apps/api/src/inventory/inventory.service.ts` (`createConsumeMovementTx`, `currentStock`), `apps/api/src/tasks/tasks.service.ts`

### 2026-07-05 — Note write RBAC: every role except Viewer may author; only the author may edit/pin/delete
**Decision**: `POST /notes` is gated to `WRITE_ROLES ∪ {STAFF}` (i.e. everyone except VIEWER) rather than the narrower `WRITE_ROLES` (OWNER/ADMIN/CHEF) used for Inventory/Recipes/Guidelines writes. `PATCH`/`DELETE /notes/:id` additionally require `existing.authorId === caller.id` — no role (including OWNER/ADMIN) gets cross-author moderation rights in this MVP.
**Why**: FR-018's literal text is "Staff can view Guidelines, manage own Tasks, and add Notes/Comments; Viewer is read-only" — this explicitly grants Staff (and by extension every non-Viewer role) note-authoring rights, unlike Inventory/Recipe/Guideline writes which FR-018 reserves for Owner/Admin/Chef. The author-only edit/delete rule is a judgment call (FR-018 doesn't grant any role explicit cross-author moderation), made consistent with the codebase's existing least-privilege default (same pattern as Task self-service in T008/T011/T019) and explicitly tested rather than silently assumed.
**Files**: `apps/api/src/notes/notes.controller.ts`, `apps/api/src/notes/notes.service.ts`

### 2026-07-05 — Announcement write RBAC is Owner/Chef-only (narrower than Notes, narrower than Inventory); read marks readBy on GET
**Decision**: `POST /announcements` is gated `@Roles(Role.OWNER, Role.CHEF)` — explicitly excluding ADMIN, unlike every other WRITE_ROLES gate in this codebase (Inventory/Recipes/Guidelines all include Admin). `GET /announcements/:id` marks the caller's id into `readBy` (a plain `String[]`, `push`-appended, checked for existing membership first to stay idempotent — not a single atomic check-and-push, so a same-user double-concurrent-read could in theory append a duplicate id, accepted as harmless since it doesn't affect read-state correctness).
**Why**: FR-021's literal text is "Owner/Chef broadcasts to all Staff, with per-user read receipts" — Admin is not named, so it's excluded rather than assumed-included. This is the third distinct RBAC shape across Inventory/Recipes/Guidelines (Owner/Admin/Chef), Notes (everyone but Viewer), and Announcements (Owner/Chef only) in this codebase — confirms the pattern that each entity's write gate must be read from its own PRD line, never copy-pasted from a prior task's shape.
**Files**: `apps/api/src/announcements/announcements.controller.ts`, `apps/api/src/announcements/announcements.service.ts`

### 2026-07-05 — Comment @mentions resolve against email local-part (no username field), strictly scoped to the caller's own Kitchen; single-level threading only
**Decision**: `Comment.entityType`/`entityId` are plain columns with no FK (matches `Note.linkedEntityType`/`Task.sourceRecipeId`), validated against a fixed `ENTITY_TYPES` enum (`recipe`/`task`/`ingredient`) at write time. `@mention` tokens are regex-extracted from the comment body and resolved by matching the local part of a member's email (case-insensitive) — this schema has no separate username field — against `prisma.user.findMany({ where: { kitchenId } })` **only**, never a global user lookup. Unresolved/non-member mentions are silently dropped, not an error. Reply threading is single-level only: a reply's `parentId` must reference a top-level comment (`parentId === null`); replying to a reply is rejected with 400 server-side, not just hidden client-side. Comment write RBAC follows the Notes/ShiftLog shape (everyone except Viewer), since FR-018 names Comments alongside Notes explicitly.
**Why**: The main security-sensitive surface here is mention resolution potentially leaking cross-tenant (resolving a same-named user in a *different* Kitchen) — scoping the lookup query itself to `kitchenId` closes this at the query level rather than filtering results after a broader fetch. Verified by a dedicated test and an independent Stage 5 live-verify session. Single-level threading avoids unbounded recursion complexity for MVP scope, enforced at the service layer (not just DTO validation) so it can't be bypassed by a client that ignores the UI's nesting limit.
**Files**: `apps/api/src/comments/comments.service.ts`, `apps/api/src/comments/comments.controller.ts`, `apps/api/src/comments/entity-type.ts`

### 2026-07-05 — Notification triggers are additive hooks into existing services; low-stock transition detection persists state on Ingredient, fires only on the read path
**Decision**: `NotificationsService#notifyMentions` is called from `CommentsService#create` right after mentions resolve (one added line, not a rewrite). `NotificationsService#notifyLowStock` is called from `AlertsService#lowStock` (T007's read endpoint) via a new private `syncLowStockState` method that diffs the freshly-computed low-stock set against a persisted `Ingredient.wasLowStock` boolean (additive column, `DEFAULT false`) — only a `false→true` flip creates a Notification (one per crossing, not per poll); a `true→false` recovery silently clears the flag with no notification. Both notification types are informational rows with no FK to their source (Comment/Ingredient), matching the established back-reference pattern. Personal-feed RBAC: `GET/POST /notifications*` has no `@Roles` gate at all — every authenticated role including Viewer can read and clear their own feed, since this is the user's own data, not a write to shared Kitchen state (contrast with the write-RBAC decisions for Notes/Announcements/ShiftLog/Comments above).
**Why**: The low-stock transition state has to live *somewhere* to detect "just crossed" vs "still crossed" — a single boolean column on the already-existing `Ingredient` row was simpler than a separate tracking table, chosen per the task's explicit "prefer the simpler shape" guidance. The known tradeoff (flagged in code-review as P2, accepted): the transition check only runs as a side effect of `GET /inventory/alerts/low-stock` being called, so a real threshold crossing isn't detected/notified until some client polls that endpoint (e.g. `LowStockWidget`) — not truly event-driven at the stock-write site. Acceptable for MVP per the guide's explicit "poll or fetch" framing; a future task could move the check to fire at the stock-movement write site instead for a tighter latency bound.
**Files**: `apps/api/src/notifications/notifications.service.ts`, `apps/api/src/inventory/alerts/alerts.service.ts`, `apps/api/prisma/schema.prisma` (`Ingredient.wasLowStock`)

### 2026-07-14 — Theme system: semantic CSS-variable tokens + data-theme attribute, account-synced via Prisma enum (T025/T026)
**Decision**: Two-theme system ("Simple" = pre-existing look, "Dark Neon" = new) implemented as: (1) backend — `User.themePreference` is a Prisma **enum** column (`Theme { simple, dark_neon }`, `@default(simple)`), not a plain String, surfaced via the `user` object in `/auth/signup`/`/auth/login` responses (no `/auth/me` route exists) and updatable via a new self-service `PATCH /users/me/theme`; (2) frontend — 9 semantic CSS custom properties (`--color-surface`, `-surface-raised`, `-text-primary`, `-text-muted`, `-accent`, `-border`, `-danger`, `-success`, `-warning`) registered via Tailwind v4's `@theme inline` in `apps/web/src/index.css`, with one `[data-theme="simple"]`/`[data-theme="dark-neon"]` CSS block per theme — components consume semantic Tailwind classes (`bg-surface`, `text-primary`) instead of raw palette classes, so a future third theme is a pure CSS diff with zero component changes. A dedicated `theme/themeMapping.ts` module is the **only** place that translates between the frontend's kebab-case `ThemeId` (`"simple"`/`"dark-neon"`, matching CSS attribute-selector syntax) and the backend's snake_case `Theme` enum (`simple`/`dark_neon`) — every API boundary crossing (auth payload in, PATCH body out) goes through it, with fallback-to-`"simple"` on null/unrecognized values in both directions. `ThemeProvider` sets `data-theme` on `<html>` synchronously before first paint from a `localStorage` cache (read by an inline script in `index.html`, before any JS module loads) — but this cache is explicitly documented as never the source of truth; the authenticated account's `themePreference` always wins once auth resolves, and the switcher does an optimistic update with rollback-on-PATCH-failure.
**Why**: A single `--color-accent` token (not split primary/secondary) was chosen because no current component uses two distinct accent roles — adding a second would be speculative (50% Rule Check, see `BRAINSTORMING_LOG_theme-system.md`). The `Theme` enum (not a String column) mirrors the existing `Role` enum convention and makes adding a future theme a deliberate, reviewed migration rather than a silent config change. Full rationale, rejected alternatives (Tailwind's binary `dark:` variant; per-component theme-prop branching), and the adversarial review are in `docs/adr/0001-theme-system-token-architecture.md`.
**Update (2026-07-14, same-day fix)**: The Dark Neon palette values in `index.css` were revised — the original ship was an invented saturated purple/hot-magenta/lime combination the user found "does not look good." Rebased on Carlos Alfaro's DarkNeon Bootstrap admin template (`github.com/Carlos007007/DarkNeon`, `css/style.css` `:root` block), which uses a tight 6-color set: near-black `#14111A` background, `#06030D` darker tone, `#2F2A3D` muted-plum border, `#EEEEEE` text, `#D51944` crimson accent (glow variant `~#FA1E4E`), `#6E6C74` muted gray. Our token *names/architecture* are unchanged (still the same 9 semantic tokens); only the Dark Neon theme's hex values changed. `--knos-text-muted` was brightened past the reference's raw `#6E6C74` (`#948fa0`) for body-text contrast on a near-black background — the reference has no dedicated status colors, so danger/success were chosen in the same magenta/teal-neon register as the accent rather than copied verbatim. ### 2026-07-06 — Task recurrence: template + occurrence model, self-relation with SetNull
**Decision**: T010 adds `Task.recurringTemplateId`/`Task.occurrenceDate` (self-relation FK, unique on the pair). A Task with `recurrenceRule` set (e.g. `"daily"`) is a *template*; a nightly job (`RecurrenceService.runNightlyGeneration`, fired by `RecurrenceScheduler`'s dependency-free hourly `setInterval` that no-ops outside UTC hour 0) clones it into today's occurrence Task. The FK is `onDelete: SetNull`, not Cascade — deleting a template preserves its generated occurrence history (matches the append-only-history pattern used for StockMovement/ShiftLog).
**Why**: Idempotency needed a DB-level guarantee (the unique constraint), not just app-level checks, so re-running the job for the same day is a safe no-op via `upsert`. The FK started as `onDelete: Cascade` in the initial implementation — Stage 4 review caught that this contradicted the edge-case test's own stated intent and the codebase's established pattern; fixed to `SetNull` and the test rewritten to exercise real deletion (previously it manually null'd the FK before deleting, sidestepping the actual cascade behavior it claimed to verify). Currently inert in practice since no `DELETE /tasks/:id` endpoint exists yet.
**Files**: `apps/api/prisma/schema.prisma` (`Task.recurringTemplateId`/`occurrenceDate`), `apps/api/src/tasks/recurrence/*`

### 2026-07-06 — Realtime (Socket.IO) reuses REST's JWT auth, kitchen-room broadcast, additive emit hooks
**Decision**: T017's `RealtimeGateway` authenticates the Socket.IO handshake via the same `JwtService`/secret as REST's `JwtAuthGuard` (no parallel WS-auth scheme), rejecting invalid/missing tokens before `connect` fires. Clients join a `kitchen:<id>` room derived from a fresh DB read of the caller's `kitchenId` (never the JWT claim — same rule as `RolesGuard`). `TasksService#update`, `CommentsService#create`, `AnnouncementsService#create` each get a one-line additive emit call (same shape as T016's notification hooks) — `emitTaskUpdated`/`emitCommentCreated`/`emitAnnouncementCreated`, each broadcast with a unique `eventId` for client-side dedupe. The server never buffers/replays events for a disconnected client — a reconnecting client only sees events emitted while it's actually connected.
**Why**: Consistency with the established "never trust a possibly-stale claim" rule, and reusing the notification-hook pattern kept the change purely additive (no existing REST behavior altered). Broadcast payloads carry no more data than the equivalent REST GET already returns to the same caller — no new field-level exposure.
**Files**: `apps/api/src/realtime/*`, `apps/api/src/tasks/tasks.service.ts`, `apps/api/src/comments/comments.service.ts`, `apps/api/src/announcements/announcements.service.ts`, `apps/web/src/lib/socket/socket.ts`

### 2026-07-14 — Team management: soft-deactivation via User.isActive, Owner/Admin protected from role-change/removal, RolesGuard deliberately NOT updated to check isActive per-request
**Decision**: T027 adds 4 Owner/Admin-only endpoints to the existing `UsersController`/`UsersService` (not a new module — matches T002's existing invite-logic placement): `GET /users` (kitchen-scoped active-member list), `PATCH /users/:id/role` (restricted to `CHEF|STAFF|VIEWER` via `@IsIn(INVITABLE_ROLES)` at the DTO layer, reusing the same constant already used for invite-time role restriction), `DELETE /users/:id` (soft-deactivation: `isActive: false`, never a hard delete — preserves FK integrity for StockMovement/Task/Comment history), `GET/DELETE /users/invites` (pending-invite list + revoke, sets `Invite.status = 'REVOKED'`, a new `InviteStatus` enum value). A `PROTECTED_ROLES = [OWNER, ADMIN]` constant blocks both role-change and removal from ever targeting an Owner/Admin — this also produces a useful side effect: an Owner/Admin cannot demote their own role via this endpoint, since their own role is itself protected. Self-removal is blocked by an explicit `callerId === targetId` check (checked before the cross-tenant/protected-role checks). `AuthService#login` now rejects `isActive: false` with the same generic 401 as a wrong password — no account-state leak.
**Why**: This deliberately does NOT close the long-standing "Owner/Admin has no creation path" gap (tracked since T002) — role-change still can't grant Owner/Admin, by explicit user decision during brainstorming. **Known accepted gap**: `roles.guard.ts` was explicitly out of scope for T027 (per its TASK_GUIDE's "Files Must NOT Touch") and does not re-check `isActive` per-request — a deactivated user's existing JWT (default `expiresIn: '1d'`) continues to authenticate on every non-login route until natural expiry. Flagged in both code-review (P1) and security-review (Medium) as the same finding; accepted as a tracked fast-follow rather than expanding T027's scope after the fact.

### 2026-07-14 — T028 frontend Team & Roles page: fetch itself gated on canManage, not just rendered controls
**Decision**: `TeamPage` reads `getUser()?.role` client-side and gates the entire `listMembers()`/`listPendingInvites()` fetch behind `canManage` (`role === 'OWNER' || role === 'ADMIN'`) — a non-manager makes zero network calls to `/users`/`/users/invites` and sees a static restricted-access message, rather than attempting the fetch and handling a 403 response. `canManageMember(member)` additionally excludes the caller's own row and any Owner/Admin row from showing role-change/remove controls, mirroring T027's server-side `PROTECTED_ROLES` guard client-side (defense in depth, not the source of truth). ### 2026-07-06 — CI/CD: deploy-hook + guard-branch job, not the Render GitHub Action
**Decision**: T023's `ci.yml` runs lint/typecheck/test/build for both `apps/web` and `apps/api` on every push/PR (api job spins up an ephemeral Postgres service container, runs `prisma generate` + `migrate deploy` before tests). `deploy-staging.yml` triggers only on `push: branches: [staging]` and additionally runs a `guard-branch` job that hard-asserts `github.ref == refs/heads/staging` before any deploy job proceeds — defense-in-depth on top of GitHub's own branch-filter allow-list. Deploy itself is a `curl -X POST` to Render's deploy-hook URLs (`RENDER_DEPLOY_HOOK_WEB`/`_API` secrets), with an optional post-deploy poll of Render's API if `RENDER_API_KEY` + service IDs are set. `prisma migrate deploy` runs against `STAGING_DATABASE_URL` before the api deploy hook fires.
**Why**: Deploy hooks are simpler than the full Render GitHub Action/API integration and sufficient for a single staging environment; the guard-branch job exists because a future accidental widening of the `on.push.branches` list (e.g. someone adds `main`) would otherwise silently start deploying to production. No real Render service/API key exists yet in this environment — a human must create the Render service(s) and add the deploy-hook/DB secrets before the staging deploy actually fires; the workflow code itself is complete and merged.
**Files**: `.github/workflows/ci.yml`, `.github/workflows/deploy-staging.yml`

### 2026-07-06 — apps/api and apps/web are standalone npm projects, no monorepo-root install needed to deploy
**Decision**: `apps/web` no longer depends on the `@kitchenos/shared` workspace package — the single type it used (`AuthResponseDto`) is now defined locally in `LoginPage.tsx`, backed by the existing `StoredUser` type in `routes/auth.ts`. Both `apps/api` and `apps/web`'s `build` scripts now explicitly run `npm install --include=dev` before the real build step. `apps/api`'s `start`/`start:prod` now point at `dist/src/main` (not `dist/main`) and `start` runs `prisma migrate deploy` before booting. `apps/web` gained a `start` script (`vite preview --host 0.0.0.0 --port $PORT`).
**Why**: The first real Render deploy failed on both counts. (2) `dist/main.js` never existed — `nest build`'s actual compiled output (given this project's `tsconfig.build.json` with no explicit `rootDir`) lands at `dist/src/main.js`; `start:prod` had pointed at the wrong path since it was first written, never caught because no one had run a real production boot from a clean build until this deploy. Removing the workspace dependency also means each app's Render service can use `Root Directory: apps/api` / `apps/web` with plain `npm run build`/`npm start`, no cross-package install step required.

### 2026-07-28 — T040: a new narrow `GET /users/assignable` instead of widening `GET /users` to CHEF
**Decision**: CHEF needed the kitchen's member list to populate the Edit Task assignee picker, but every route on `UsersController` is `@Roles(OWNER, ADMIN)` (T027 team management). ### 2026-07-28 — T043: invite delivery is copy-link, out-of-band; no mailer is added
**Decision**: There is no mail infrastructure in this project and none was added. `TeamPage` now renders a copyable `${origin}/invite/accept?token=…` link — after inviting **and** on every pending-invite row — and the Owner sends it themselves via Slack/WhatsApp/SMS. The pending-row link matters as much as the post-invite one: a one-shot success message is lost on reload, which would strand an Owner holding an undeliverable invite.

Decision

Problem: KitchenOS's MVP spans ~10 interrelated entities with RBAC across 4 roles, cost roll-up logic, recurring task generation, and near-real-time collaboration — what architecture direction fits a solo, greenfield, local-dev-only build without over- or under-building?
Option B — The Structured Path: NestJS backend + React frontend in a monorepo (/apps/web, /apps/api, /packages/shared), Socket.IO for realtime, cron-based recurring task generation.
Matches the domain's actual shape (RBAC-heavy, ~10 entities, real-time collaboration is a named MVP requirement in PRD §3.3) without paying for microservice-level distributed-systems overhead that no current requirement calls for. NestJS's guards/DI give one consistent RBAC enforcement point instead of 10+ hand-rolled per-route checks. The monorepo keeps API contract types shared for a solo dev. Cron-generated Task rows keep per-occurrence completion and stock deduction (FR-008's confirm-prompt) simple to model, avoiding the complexity of virtual/on-the-fly recurrence instances.

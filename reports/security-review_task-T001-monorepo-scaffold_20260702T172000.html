Medium docker-compose.yml 9–10 
Insecure Configuration — Postgres exposed with default credentials on all interfaces.

docker-compose.yml mapped "5432:5432" without binding to 127.0.0.1, so Postgres listened on 0.0.0.0:5432 on the host — reachable from any device on the same local network, not just the host machine. Combined with hardcoded default credentials (kitchenos/kitchenos), any host on the LAN could connect directly to the database.

Exploit scenario: a device on the same network/subnet as the dev machine (shared office wifi, coworking space, compromised IoT device on the same subnet) connects via `psql -h <ip> -U kitchenos kitchenos` with password `kitchenos`, gaining full read/write access — including user emails and bcrypt password hashes.

STATUS: FIXED — bound to 127.0.0.1:5432:5432 in commit f492ee9, verified via `docker port kitchenos-postgres` (now shows 127.0.0.1 only) and re-ran the auth test suite (10/10 passing) against the rebound container.
Security review of T001 (monorepo scaffold + auth skeleton, ~40 files) found no high-confidence exploitable vulnerabilities in the newly-added authentication logic itself: Prisma ORM is used for all DB access (no SQL injection surface), JWT secret is sourced from a trusted environment variable, ValidationPipe with whitelist+transform is applied globally, bcrypt with 10 salt rounds hashes passwords, and the React frontend renders no unescaped content (no XSS surface). The RBAC/authorization gap (JwtAuthGuard is "is authenticated" only, no role checks) is an explicitly documented and intentional deferral to T002 per the task guide — not a vulnerability newly introduced to hide. One concrete Medium-severity finding was identified and fixed during this review: docker-compose.yml bound Postgres to all network interfaces (0.0.0.0) rather than localhost, exposing the local-dev database — with default weak credentials — to the entire local network. This was corrected to bind 127.0.0.1 only, verified against the running container, and the full auth test suite was re-run successfully against the rebound database to confirm no regression.

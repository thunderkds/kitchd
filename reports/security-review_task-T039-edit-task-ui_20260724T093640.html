Security review of T039 (Edit Task UI) - RESULT: PASS. No security findings block merge. The change is frontend-only: 9 files under apps/web/src/features/tasks/, with no backend, Prisma schema, migration, or auth-guard file touched. It introduces no new endpoint and no new server-side attack surface; it surfaces an affordance for PATCH /tasks/:id, an endpoint that has existed since T008 and whose RBAC was corrected in T019. The central question for a Medium-risk, RBAC-adjacent task is whether the new client-side role gate is being relied on as a security control. It is not. The gate exists purely so that a control which would always 403 is not rendered - a UX concern - and the code says so explicitly. Enforcement remains entirely in TasksService.update, which was read directly during this review to confirm the three-way split: WRITE_ROLES may change any field, STAFF only status and checklistItems and only on a task assigned to them, VIEWER never. The client mirrors that split rather than inventing a fourth shape, which matters in this codebase specifically: memory records at least four distinct RBAC shapes and prior bugs caused by copying one feature's shape onto another. Two data-flow paths were traced in full. First, assignee options: both sources are kitchen-scoped, so no cross-tenant identifier can enter the picker, and the fetch of GET /users is itself gated to OWNER/ADMIN to match the server's @Roles decorator - a Chef falls back to ids already visible on their own tasks rather than triggering a 403. Second, the PATCH payload: every field passes through UpdateTaskDto under a global whitelisting ValidationPipe, so client-supplied extras are stripped before reaching Prisma, and assigneeId is independently re-validated against the caller's kitchen. Worth preserving, though not itself a security control: the dialog deliberately omits a status field so a task cannot be driven to DONE without passing through T011's preview/confirm flow. Bypassing that would skip the stock deduction required by FR-008. That is a business-integrity safeguard, and future edits to this dialog should not quietly reintroduce a status control.

Decision

Problem: How should a multi-theme system ("Simple" + new "Dark Neon", switchable per-user, extensible to future themes) be architected in `apps/web`, which today has zero theming infrastructure — no CSS variables, no theme context, all color hardcoded as raw Tailwind palette classes across 17 files?
Option B — Semantic CSS-variable tokens + data-theme attribute, account-synced via a new Prisma enum User.themePreference.
This is the only option that satisfies "future themes can be added easily" without a rewrite, and it happens to also be the industry-standard pattern for Tailwind v4 theming (@theme inline + CSS custom properties + data-theme). It centralizes color definitions that today don't exist at all, which is a genuine simplification of the current ad-hoc state, not just new complexity for its own sake. Adding theme #3 later becomes a pure CSS diff plus one enum-value migration — zero component code changes, because components only ever reference semantic tokens (bg-surface, text-primary) rather than raw palette classes.

Assumptions & Open Questions

  • Resolved Persistence is account-synced (DB-backed User.themePreference), not browser-only localStorage — user explicitly requested cross-device sync.
  • Resolved Full migration of all 17 raw-color files happens in this task, not incrementally — avoids a half-themed UI where Dark Neon looks broken on unmigrated screens.
  • Resolved Theme switcher control lives on the settings/profile page, not a topbar quick-toggle.
  • Resolved Accent token stays a single --color-accent (not split primary/secondary) — no current component uses two distinct accent roles.
  • Resolved Theme identifiers are kebab-case strings "simple" / "dark-neon", matching CSS attribute-selector syntax directly.
  • Resolved themePreference is a Prisma enum column (Theme { simple, dark_neon }), not a plain String — matches the existing Role enum convention; adding a future theme requires a migration by design.
  • Assumption No cross-tab live-sync requirement — if a user changes theme in one open tab, other open tabs are not expected to update in real time for MVP.
  • Deferred Pre-auth / logged-out flash-of-wrong-theme handling and the exact fallback default (existing users with unset themePreference) are flagged as Edge Cases for the TASK_GUIDE, not fully solved during brainstorming.
